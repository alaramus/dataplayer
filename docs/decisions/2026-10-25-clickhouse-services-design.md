# ClickHouse services

Decision D280. The second half of the sixth slice of the ClickHouse source: a
server started on this machine, and the lab it may open on.

## The template

The official image, at the long-term-support release the suite runs against.
Only the HTTP interface is published: the source type speaks nothing else, and
a native port nobody connects to is a port somebody has to think about.

The image makes its `default` user with the password it is given, and with
`CLICKHOUSE_DEFAULT_ACCESS_MANAGEMENT` that user may make users and grant
rights. An ordinary user the image could make instead would be the one
account on a server that is entirely its owner's, which is the argument MySQL's
template made for root (D244).

The image asks for a large limit on open files and warns without one; it runs
all the same, and a template sets no limits on its container, so none is set.

The limits a container does get are the server's own, 512 processes among them
(D86). ClickHouse 25.8 starts a schedule pool of 512 threads and aborts when it
cannot, so the server is sized to the limit rather than the limit to the
server. `--background_schedule_pool_size` on the command line is applied and
then lost: the configuration is reloaded from its files, and the pool grows
back to 512. A file in `config.d` survives the reload. A template carries no
files, so its command is a shell that writes one and execs the image's own
entrypoint, which still sets up the user and the database. Measured under
those limits it idles at about 230 processes and stays under 250 while loading
five million rows.

## The lab

The same story as PostgreSQL's and MySQL's: organizations, people, projects and
their tasks. What ClickHouse is for is reading a great many rows, so the lab
also holds two hundred thousand page views, generated by the server from
`numbers()` rather than shipped as rows, spread over three months up to the
moment it is installed so that the partitions and the TTL mean something.

Two materialized views read the page views: one feeds a SummingMergeTree table
of its own (`TO`), one keeps its rows in an inner table. They are made before
the page views are inserted, so both are filled. Tasks are a
ReplacingMergeTree with two of them written twice, and the view over projects
reads them with `FINAL`, so the grid shows the duplicates and the view does
not.

## One rule for splitting a script

MySQL's lab is split where a line ends in a semicolon (D245); ClickHouse's is
written to the same rule, so the splitting moved to a module both adapters
import rather than being copied.
