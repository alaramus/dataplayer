# Модель отношения

Дата: 2026-08-24
Статус: согласовано
Раунд: 8

## Цель

Приложение делает упор на базы данных, а знает о таблице четыре факта: имя
колонки, тип строкой, nullable и признак первичного ключа. Этого не хватает
почти ничему из запланированного: гриду нужен ключ записи и поведение по типу,
переходам по внешним ключам — связи, редактированию структуры — DDL, диаграмме
схемы — граф.

Раунд вводит одну вещь: **источник умеет описать своё отношение целиком**. Всё
перечисленное потом берёт описание отсюда, а не добывает заново.

## Что нашлось в старом приложении

`GET_SYSTEM_ALL_COLUMN_INFO` — ключ шаблона, который есть у каждого
SQL-адаптера: postgres, clickhouse, duckdb, mssql, oracle. Один вопрос, у
каждого диалекта свой ответ. Это прямо просится в способность.

Сам запрос postgres одним проходом по `pg_attribute` даёт тип, `udt_name`,
физическое хранение, длину, nullable, генерируемость, дефолт, вид ограничения,
цель внешнего ключа и агрегированный список индексов по колонке. Идея верная, и
переносится она.

Переносятся не все решения. Два места сломаны, и оба воспроизводить нельзя.

**Первое — имя типа.** Модель отдавала два имени, и ни одно не годится для
`CREATE TABLE`:

| Что в запросе | `integer[]` | `varchar(50)` |
| --- | --- | --- |
| `t.typname` (`udt_name`) | `_int4` | `varchar` |
| `atttypid::regtype` | `integer[]` | `character varying` — модификатор потерян |
| `format_type(atttypid, atttypmod)` | `integer[]` | `character varying(50)` |

`_int4` — внутреннее имя массива в `pg_type`, в DDL его подставить нельзя.
Починку видно в коде: `EXACT_DEFINITION_TYPES` с `atttypid::regtype` зовётся
только из `backup_utils.py`, то есть там, где пишется DDL, отдельным запросом на
каждую колонку и с подстановкой имени таблицы через `.format`. Заплатка на том
самом месте, и неполная: `varchar(50)` она превращает в `character varying`.

**Второе — составные ключи.** `LEFT JOIN pg_constraint ON attnum = ANY(conkey)`
даёт строку на каждую пару «колонка × ограничение», а составной внешний ключ
разложен по колонкам через `array_position(conkey, attnum)`. Связь из двух
колонок представлена как две независимые. Для перехода по такому ключу это
неверно: переходить надо по паре значений сразу.

## Решения

### Р1. Описание отношения — отдельная способность

```python
@runtime_checkable
class SupportsRelationModel(Protocol):
    async def relation_model(self, node_id: str) -> RelationModel: ...
```

Рядом с `SupportsCatalog` и `SupportsFetch`, по букве D2: контракт требует
минимум, остальное — независимые способности. Файловый источник её не реализует
и отвечает 501 тем же кодом, которым уже отвечает на всё, чего не умеет.

Отвергнуто включение в `SupportsCatalog` («умеешь показывать детей — умей
описать таблицу»): очередь и объектное хранилище имеют каталог и не имеют
отношений вовсе.

Отвергнута выдача модели вместе с `FetchResult`: модель тяжелее страницы строк и
меняется несоизмеримо реже, а слать её с каждой страницей — платить полную цену
на каждом пролистывании.

### Р2. Тип колонки — объект, а не строка

Одна строка не может делать три работы: показать человеку, решить поведение,
попасть в DDL. Старое приложение пыталось, и разобранная выше поломка — цена
попытки.

```
ColumnType
  sql: str        # format_type(atttypid, atttypmod) — то, чем пишет типы pg_dump
  category: Literal["number","string","boolean","datetime","binary","json",
                    "uuid","network","geometric","range","enum","composite",
                    "array","other"]
  element: ColumnType | None    # когда category == "array"
  dimensions: int = 0
  enum_values: list[str] | None      # когда category == "enum"
  length: int | None                 # varchar(50) -> 50
  precision: int | None              # numeric(10,2) -> 10
  scale: int | None                  # numeric(10,2) -> 2
```

`category` — то место, где грид перестаёт разбирать строку типа регулярным
выражением, а фильтры перестают предлагать `contains` для `int`. Считается один
раз на сервере: одно и то же вычисление на бэкенде и на фронте — дефект по
ENGINEERING.md.

Берётся из `pg_type.typcategory`, где уже есть `A` массив, `B` булево, `C`
составной, `D` дата, `E` перечисление, `G` геометрия, `I` сеть, `N` число, `R`
диапазон, `S` строка. Отдельной таблицей разбирается то, что Postgres валит в
`U`: `json`, `jsonb`, `uuid`, `bytea`.

`typname` в модель не кладётся вовсе. Поле есть — рано или поздно его подставят
в DDL, ровно как вышло в старом приложении. Появится настоящая нужда — добавится
под именем, которое нельзя перепутать с писабельным.

### Р3. Ограничение — объект верхнего уровня

Дискриминированный union по `kind`, как `CatalogNode`:

- `primary_key` — имя, упорядоченные колонки;
- `unique` — имя, колонки, `nulls_not_distinct`;
- `foreign_key` — имя, свои колонки, `target_node_id`, чужие колонки,
  `on_update`, `on_delete`, `match`;
- `check` — имя, выражение, задействованные колонки;
- `exclude` — имя, выражение.

Порядок колонок берётся из `conkey` как есть и никогда не сортируется — это то,
что в старом приложении разваливало составной ключ. На колонке остаются только
ссылки на ограничения, а не их копии: склейка на клиенте, которая была в
`allConstraints`, исчезает.

### Р4. Внешний ключ несёт `target_node_id`

Не пару «схема + таблица», из которой клиент соберёт идентификатор сам. Это
буква D21: источник говорит, где живёт узел, клиент id не разбирает и не
собирает. Строит его адаптер, в том же виде, в каком выдаёт каталог.

Ради этого одного решения переход по ключу в гриде потом не потребует второго
проектирования — только экрана.

### Р5. Запрос написан над множеством отношений, а зовётся по одному

Приватный `_models(schema, relation: str | None)`: join через `pg_namespace`,
фильтр по имени отношения — необязательный предикат. Публичный `relation_model`
зовёт его с именем и возвращает одну модель.

Короткий путь — `WHERE attrelid = %s::regclass`, по одному oid — запрещён именно
потому, что не обобщается: схема целиком потребовала бы переписать запрос, а не
убрать предикат. Схема за раз появится вместе с кешем и будет тем же вызовом без
имени.

Четыре запроса, последовательно: отношения, колонки, ограничения, индексы.
Параллельно нельзя — они делят одно соединение из пула, а psycopg на одном
соединении не мультиплексирует.

Ничего не строится форматированием строк: идентификаторы через `sql.Identifier`,
значения через плейсхолдеры (D2c). Отношения нет — `NodeNotFound`, то есть 404, а
не 502: узел мог быть удалён, пока открыта вкладка.

### Р6. Каталог перестаёт спускаться в таблицу

`ColumnNode` сегодня строится запросом `_list_columns` и не показывается никому:
`nodes.ts` ставит колонке роль `hidden`, и на фронте её не читает ничего. То есть
это второй запрос за теми же фактами, который может разойтись с первым, ради
результата, которого не видно.

`_list_columns` и `ColumnNode` удаляются, `TableNode.has_children` становится
`false`. Экран не меняется: таблица и сейчас `leaf`.

`fetch._columns` остаётся и комментируется как намеренно отдельный. Он описывает
**результат**, а не отношение: результатом позже может быть произвольный запрос,
у которого модели нет вообще. Это разные вещи, а не дублирование.

### Р7. Структура — отдельный вид панели

`structure` в закрытый union панелей, свой компонент, свой `structurePanelId`.
Тест рядом с `panels.ts` падает, если вид добавлен без компонента.

Отвергнут переключатель «Строки / Структура» внутри панели `rows`: он отнимает
то единственное, ради чего в этом приложении вкладки таскаются мышью —
возможность положить структуру рядом со строками в соседней колонке.

Отвергнуто «сделать модель, экран потом»: тогда из тридцати полей человек увидит
ноль, а рабочее правило говорит прямо — зелёный юнит-тест не значит, что
результат виден. Так уже вышло с подписями в дереве.

### Р8. Кеша в этом раунде нет

Модель — чистое значение, адресуемое парой `(коннектор, node_id)`, так что кеш
позже ложится обёрткой и ничего не переписывает. На клиенте vue-query кеширует
её сам, длинным `staleTime` (D6).

Серверный кеш не вводится: он приносит задачу устаревания — DDL меняет модель —
а измерений, что это нужно, пока нет. Это следующий раунд, вместе со схемой за
раз из Р5.

## Что делается

**Сервер.** `app/adapters/relation.py` — типы модели, без SQL; имя `relation`, а
не `model`, чтобы не путалось с моделями базы приложения.
`SupportsRelationModel` в `adapters/protocol.py`.
`app/adapters/postgres/relation.py` — четыре запроса и сборка. `_list_columns` и
`ColumnNode` вон из `postgres/catalog.py` и `adapters/catalog.py`.
`GET /connectors/{id}/relation-model?node_id=...` в `connectors/routes.py`, по
образцу `/catalog`: 501 без способности, 404 на исчезнувший узел, 502 на отказ
источника. Строка в `capabilities_of`.

Состав модели: отношение — схема, имя, вид, комментарий, владелец,
долговечность, оценка строк, размер, секционирование, родитель-секция; колонка —
позиция, имя, комментарий, тип по Р2, nullable, дефолт, `identity`, `generated` с
выражением, сортировка, физическое хранение; индекс — имя, колонки или
выражение, метод, уникальность, частичный предикат, валидность. Везде
`extra="forbid"`, как у `CatalogNode`.

**Экран.** `features/structure/api.ts` — `useRelationModel` на vue-query;
`features/structure/model.ts` — чистые функции: разложить ограничения по
колонкам, решить значки колонки, собрать подпись внешнего ключа;
`features/structure/StructureView.vue`;
`features/workspace/panels/StructurePanel.vue` плюс `structure` в union и
`structurePanelId`; `openStructure` рядом с `openRows` в `workspaceActionsKey`,
вызывается из `CatalogPanel` вторым действием на узле-таблице. Клиент
перегенерируется `scripts/generate-client.sh`.

**Документация.** D22 в таблицу AGENTS.md, дом в
`docs/architecture/adapters.md`, строка в «What already works».

Места для этого не было: в AGENTS.md оставалось 142 байта. Первым кандидатом на
вынос оказалась ловушка про `vue-tsc` — то есть бюджет собирался вытолкнуть
ровно то, ради чего файл грузится в каждую сессию. Значит потолок стоял низко, а
не файл разросся. Он поднят с 16 КБ до 24 КБ в `scripts/check-docs.sh`,
отдельным изменением и с записанной причиной: ослабление проверки по дороге к
зелёному прогону — это то, что ENGINEERING.md запрещает, а осознанная смена
неверного правила — нет.

## Чем проверяется

Фикстура — таблица с заведомо неудобной структурой: `integer[]`, `varchar(50)`,
`numeric(10,2)`, перечисление, генерируемая колонка, `identity`, составной
первичный ключ и составной внешний.

Сервер:

- **круг через DDL**, главный тест раунда: взять `type.sql` из модели, собрать
  `CREATE TABLE`, выполнить, прочитать модель новой таблицы, сравнить типы.
  `_int4` его не проходит, `character varying` без `(50)` — тоже;
- составной внешний ключ приходит одним ограничением с упорядоченными
  колонками, а не двумя связями;
- `category` для массива, перечисления, `jsonb`, `uuid`, `numeric`;
- `enum_values` перечисления, `element` и `dimensions` массива;
- у представления есть колонки и нет ограничений;
- удалённое отношение — `NodeNotFound`, маршрут — 404;
- файловый источник — 501; `capabilities_of` называет новую способность;
- существующие тесты каталога зелены после удаления `_list_columns`.

Экран:

- `model.spec.ts`: ограничения разложены по колонкам; колонка в трёх
  ограничениях получает три значка; подпись внешнего ключа называет цель;
- Playwright, и это единственное настоящее доказательство: открыть структуру
  таблицы из каталога, увидеть колонку с типом, значок первичного ключа и строку
  внешнего ключа с именем цели; перетащить вкладку структуры в соседнюю колонку
  и увидеть её рядом со строками.

## Чего в раунде нет

- кеша, ни серверного, ни схемы за раз;
- переходов по внешним ключам в гриде — модель их только описывает;
- редактирования структуры и любого DDL;
- специфики расширений: гипертаблицы Timescale и прочее — отдельная способность;
- файлового источника: у него свои пределы, и это отдельный раунд;
- триггеров, правил и прав на отношение.
