# Реестр действий

Дата: 2026-08-21
Статус: согласовано
Подпроект: 5

## Цель

До сих пор приложение только читает. Реестр действий отвечает на вопрос «что
можно сделать с этим узлом» так, чтобы ответ приходил с сервера, а интерфейс
строился из него без единого ветвления по типу источника.

Первые настоящие действия — запись в личное хранилище: создать папку,
переименовать, удалить, загрузить файл. Тем самым закрывается известное
отклонение «в личную директорию ничего не пишет»: до сих пор её наполнял
только `seed_storage` с сервера.

PostgreSQL в этом подпроекте не получает ни одного действия. Это не пробел, а
проверка: источник без реестра должен отвечать 501, а не притворяться.

## Что выяснилось про старое приложение

Разбор `webapi/view.py:70`, `core/supported_actions.py` (765 строк) и
`webapi/view_services/connector_actions.py` дал пять фактов, и каждый здесь
закрывается решением.

**Диспетчеризация — `getattr(connector, action)`.** Клиент присылает имя
метода адаптера, и оно вызывается: `performer = getattr(connector, action)`,
`await performer(**params)`, где `params` — тело запроса целиком. Вызвать
можно любой публичный метод объекта, а не только задуманный как действие.

**Декларация и вызов разошлись.** Единственная защита — `if not
hasattr(connector, action)`. Словарь `ACTIONS` на 765 строк, где для каждого
типа перечислено, что он умеет, в проверке не участвует вовсе: он украшает
интерфейс, а не ограничивает вызов. Новый метод становится вызываемым, не
будучи нигде объявленным.

**Имя действия несёт структуру строкой.** `custom_form::BinanceSymbol`,
`custom_form::PostgresForm::postgresql.conf` — описание формы, зашитое в имя и
разбираемое расщеплением по `::`.

**Действия объявлены у типа источника, а не у вида узла.** Списки заданы
парами `connectors` / `get_catalog`, почти всегда дословными копиями друг
друга. Поэтому `upload` предлагается на файле, а `download` — на папке:
различить их нечем.

**Параметры не типизированы нигде.** `params = {**data, ...}` уходит в метод
как `**kwargs`; что именно действие принимает, известно только из его тела.

## Решения

### Р1. Объявление и есть точка вызова

Действие — объект, который держит вместе имя, заголовок, модель параметров и
`run`. Реестр хранит эти объекты; вызвать можно только то, что в нём лежит.
Разойтись, как `ACTIONS` с `hasattr`, декларации и вызову негде: это одна
запись.

```python
class Action[P: BaseModel](ABC):
    name: ClassVar[str]
    title: ClassVar[str]
    applies_to: ClassVar[frozenset[NodeKind]]
    destructive: ClassVar[bool] = False
    params_model: type[P]

    async def perform(self, node_id: str | None, raw: Mapping[str, Any]) -> ActionResult:
        return await self.run(node_id, self.params_model.model_validate(raw))

    @abstractmethod
    async def run(self, node_id: str | None, params: P) -> ActionResult: ...
```

Абстрактный класс здесь, а не протокол, намеренно. Он делает ровно одно —
валидирует параметры моделью действия до вызова `run`, за счёт чего
диспетчеризация типизируется под `--strict`: наружу торчит `Mapping[str, Any]`,
внутрь `run` приходит конкретная модель. Отказ от наследования в решении D2b
касался драйверов с бизнес-логикой, растущей по многим осям; здесь наследуется
двадцать строк валидации, у которых оси роста нет.

### Р2. Действия — очередная необязательная возможность

```python
@runtime_checkable
class SupportsActions(Protocol):
    async def available(self, node_id: str | None) -> list[Action[Any]]: ...
    def action(self, name: str) -> Action[Any]: ...
```

Рядом с `SupportsCatalog` и `SupportsFetch`, по тому же правилу: маршрут
проверяет возможность и отвечает 501, если её нет. PostgreSQL протокол не
реализует.

`available` возвращает объекты действий, а не имена: заголовок и схему
параметров маршрут получает из них же, а не из второго источника правды.

**Уточнено при реализации.** В протоколе задумывался третий метод — `run`,
которым адаптер выполнял бы действие по имени. Он оказался лишним слоем: раз
`action(name)` уже возвращает сам объект, маршрут вызывает его напрямую, и
разрешать имя во второй раз негде. Меньше методов — меньше мест, где имя может
быть разрешено иначе.

### Р3. Применимость спрашивается у сервера по конкретному узлу

`GET /connectors/{id}/actions?node_id=…`. Сервер решает, что применимо, и той
же функцией проверяет при выполнении — правило живёт в одном месте.

Отвергнуто: раздавать списки статически в `GET /adapter-types` и сопоставлять
с видом узла на фронтенде. Тогда правило применимости оказывается и в фильтре
клиента, и в проверке сервера, а это ровно тот случай, который ENGINEERING.md
называет дефектом.

Отвергнуто: класть список действий в каждый узел каталога. `CatalogNode`
описывает то, что есть, а не то, что можно; листинг из тысячи файлов вырос бы
на тысячу одинаковых списков.

Запрос по узлу выбран ещё и потому, что применимость зависит не только от вида
узла, но и от его состояния: корень коннектора — обычная папка, но удалить или
переименовать его нельзя. Драйвер убирает такие действия из ответа сам.

### Р4. Транспорт объявляется протоколом, а не полем

У загрузки тело — байты, а не JSON. Действие, принимающее файл, реализует
дополнительный протокол:

```python
class FilePayload(Protocol):
    filename: str | None
    async def read(self, size: int) -> bytes: ...


@runtime_checkable
class TakesFile(Protocol):
    async def perform_with_file(
        self, node_id: str | None, raw: Mapping[str, Any], payload: FilePayload
    ) -> ActionResult: ...
```

Поле `takes_file` в ответе API **выводится** проверкой `isinstance`, как
`secret_field_names` выводится из `SecretStr`, а не проставляется рукой:
объявление и реализация не могут разойтись.

`FilePayload` — собственный протокол, а не `fastapi.UploadFile`, которому он
структурно удовлетворяет. Драйвер не должен знать про веб-фреймворк, а тест —
поднимать его, чтобы передать десять байт.

Ручек две, потому что у HTTP две формы тела, и каждая отказывает действию
чужого транспорта. Список «что здесь можно сделать» при этом остаётся один.

### Р5. Куда перечитать дерево, решает сервер

```python
class ActionResult(BaseModel):
    message: str
    reload_node_id: str | None   # чью ветку перечитать; None — корень коннектора
```

Каждое из четырёх действий меняет содержимое ровно одной директории, и какой
именно — знает тот, кто действие выполнил. Клиент это не выводит из имени
действия.

### Р6. Имя из формы судится тем же правилом, что сегмент пути

`create_folder` принимает `name`, `rename` — `new_name`, загрузка приносит
`filename` внутри multipart. Все три — строки от клиента, и все три проходят
через `is_plain_name` из `file/session.py` — правило заодно стало публичным и
строже: сегмент с разделителем любой из двух платформ теперь тоже
отклоняется, — после чего результат разрешается через `session.resolve`. Новых правил пути не заводится: граница остаётся
одна, как и обещано решением D8.

Отдельно про загрузку: имя файла из multipart — это тоже клиентская строка, и
`../evil` в нём должно отклоняться так же, как в `node_id`.

### Р7. Разрушительность объявляется, подтверждение генерическое

`destructive: bool` в объявлении действия. Диалог показывает подтверждение по
этому флагу, а не по списку имён вроде `ws_actions` в старом маршруте.

Флаги `recursive` и `overwrite` живут в схеме параметров и по умолчанию
`false`: непустая папка и занятое имя дают отказ, пока пользователь не скажет
иначе явно. Защита от потери данных — на сервере; клиент лишь рисует
галочку, которую схема и так описывает.

## Действия файлового источника

Новый модуль возможности `adapters/file/actions.py` рядом с `catalog.py` и
`fetch.py` (решение D2b): сессия ничего не знает о действиях, действия — о
соединении.

| Действие | Применимо к | Параметры | Отказ |
| --- | --- | --- | --- |
| `create_folder` | directory | `name` | имя занято → 409 |
| `rename` | directory, file | `new_name` | имя занято → 409; корень → 422 |
| `delete` | directory, file | `recursive: bool = False` | непустая папка без флага → 409; корень → 422 |
| `upload` | directory | `overwrite: bool = False` + файл | имя занято без флага → 409; больше потолка → 413 |

**Загрузка идёт потоком.** Чанки читаются из запроса и пишутся через
`to_thread.run_sync` во временный файл в той же директории, затем
`os.replace` — читатель каталога никогда не видит наполовину записанный файл
под настоящим именем. Потолок — настройка `MAX_UPLOAD_BYTES`; при превышении
временный файл удаляется, а ответ — 413. Размер считается по мере чтения, а не
берётся из заголовка: заголовку клиента верить нельзя.

**Весь ввод-вывод — через `to_thread.run_sync`**, как в каталоге и чтении.
`open()` в `async def` ловит ruff, `os.mkdir` и `os.replace` не ловит никто.

## API

```
GET  /api/v1/connectors/{id}/actions?node_id=…      → list[ActionInfo]
POST /api/v1/connectors/{id}/actions/{action}       → ActionResult
POST /api/v1/connectors/{id}/actions/{action}/file  → ActionResult
```

```python
class ActionInfo(BaseModel):
    name: str
    title: str
    destructive: bool
    takes_file: bool
    params_schema: dict[str, Any]
```

`params_schema` — JSON Schema модели параметров, та же форма ответа, что у
`GET /adapter-types`, и рисует её тот же `SchemaForm`.

Коды ответа — по одному правилу на причину:

| Код | Причина |
| --- | --- |
| 501 | источник не реализует `SupportsActions` |
| 404 | нет коннектора; нет такого действия у этого источника |
| 422 | действие неприменимо к узлу; путь вне корня; параметры не прошли схему |
| 409 | имя занято; непустая папка без `recursive` |
| 413 | превышен потолок загрузки |
| 415 | действие вызвано ручкой чужого транспорта |
| 502 | `AdapterError` от источника |

409, 422 и 413 приходят из одного исключения с полем причины, а не из трёх
разных: отображение причины в код лежит в маршруте, одной таблицей.

## Фронтенд

`SchemaForm/` переезжает из `features/connectors/` в `shared/`. Это его второе
применение — тот самый момент, когда обобщение оправдано, а не преждевременно;
иначе `catalog` начал бы импортировать `connectors`, и связь между
возможностями пошла бы вбок.

Панель над деревом строится из ответа сервера: по кнопке на действие, диалог с
формой параметров, подтверждение при `destructive`, выбор файла при
`takes_file`. Ветвления по типу источника нет нигде.

После успеха перечитывается ветка `reload_node_id`. Инвалидации vue-query
недостаточно: QTree держит детей в самих узлах, поэтому нужен `reload(nodeId)`,
который перезапрашивает детей и подменяет `node.children`. Это уже известное
свойство экрана, а не открытие подпроекта.

## Чем проверяется

Бэкенд:

- недекларированный метод драйвера через API невызываем;
- неизвестное имя действия → 404, у PostgreSQL любое действие → 501;
- параметры мимо схемы → 422 с `loc`, указывающим на поле;
- счастливый путь каждого из четырёх действий в временной директории;
- `..`, абсолютный путь, сегмент с буквой диска и симлинк наружу — и в
  `node_id`, и **в имени файла из multipart**;
- удаление и переименование корня коннектора → 422;
- занятое имя → 409; непустая папка без `recursive` → 409; после отказа файлы
  на месте;
- превышение `MAX_UPLOAD_BYTES` → 413, временный файл не остался;
- действие с файлом на JSON-ручке и наоборот → 415;
- коннектор чужого пользователя → 404, и в тексте ошибки нет абсолютного пути
  сервера;
- `mypy --strict`, `ruff`, `lint-imports` чисты.

Фронтенд: юнит-тест чистого маппера ответа в описания кнопок; сценарий
Playwright — создать папку и увидеть её в дереве, загрузить файл и открыть его
в сетке, переименовать, удалить с подтверждением.

## Чего в подпроекте нет

- скачивание и потоковая отдача — подпроект 7;
- перемещение и копирование между узлами и между коннекторами;
- квоты и учёт занятого места;
- прогресс загрузки и возобновление;
- действия у PostgreSQL;
- журнал выполненных действий;
- пагинация детей каталога и пул соединений — по-прежнему подпроект 4б.
